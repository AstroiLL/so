## 1) Контекст проекта

- Название: Second Opinion
- Тип: Telegram-first медицинский ассистент с backend-first архитектурой
- Технологический контур: n8n для оркестрации, Supabase (PostgreSQL + RLS), Telegram Bot API, LLM через n8n OpenAI node
- Основные артефакты: JSON Schema для AI-ответов и рекомендаций, ERD/DDL Supabase, нотация статусов с enum’ами, DLQ и идемпотентность в n8n
- Цель MVP: безопасный intake, нормализация данных, генерация структурированных рекомендаций (summary, red flags, lifestyle, self-care, talk-to-doctor, next steps, confidence, disclaimer) и диалог в Telegram

## 2) Архитектурные принципы (non-negotiable)

- Backend-first. Логика, валидация и контракты — на стороне бэкенда и схем данных. Telegram — транспорта и UX‑слой.
- Поток событий через n8n. Все бизнес-флоу — как явные workflow’ы. Обязательны: Retry с экспоненциальной паузой, DLQ, идемпотентность по messageId/композитным ключам.
- Договоры данных первичны. Любые AI-ответы должны соответствовать утверждённым JSON Schema. Любые изменения — через миграции и версионирование схем.
- Supabase как источник истины. Жёсткое соблюдение RLS, разделение PII и доменных данных, минимизация surface area REST/RPC.
- Детерминированные интеграции. Внешние вызовы (LLM, Telegram, Supabase) — обёрнуты в клиенты с явной сериализацией, логированием и контролем ошибок.
- Наблюдаемость и аудит. Полный audit log для критических операций; корреляция по userId/sessionId/messageId.
- Безопасность по умолчанию. Минимальные привилегии, секреты только в n8n credentials, строгие политики доступа к данным пользователя.
- Прозрачная эволюция. Любые изменения контракта/схемы/конституции — через PR, чек‑лист обновления, семантическое версионирование.

## 2.1) Языковые стандарты и локализация

**Русский язык как основной**

- Все пользовательские интерфейсы в Telegram должны быть на русском языке: команды, кнопки, сообщения, инструкции.
- AI-ответы генерируются исключительно на русском языке. Системные промпты содержат явное указание: "Отвечай только на русском языке".
- Структурированные поля в JSON Schema (summary, red_flags, lifestyle рекомендации) заполняются на русском.
- Дисклеймеры и предупреждения формулируются на русском с учетом российского медицинского контекста.

**Техническая документация и код**

- Названия переменных, функций n8n-воркфлоу — на английском для совместимости.
- Комментарии в коде n8n и SQL-схемах — на русском для удобства команды.
- Логи системы — на английском с русскими пояснениями при необходимости.

**Обработка данных пользователя**

- Входящие сообщения от пользователей принимаются на русском языке.
- Валидация и нормализация текстовых полей учитывает кириллицу и русскую морфологию.
- Полнотекстовый поиск в БД настраивается под русский язык (PostgreSQL russian configuration).

**Контроль качества языка**

- AI-промпты включают инструкции по стилю: "Используй медицинскую терминологию, понятную обычному пользователю".
- Ответы должны соответствовать российским культурным особенностям и ментальности в отношении здоровья.
- Тестирование включает проверку корректности русского языка в AI-ответах.

**Масштабирование**

- Архитектура позволяет добавление других языков через параметр user.preferred_language в будущем.
- JSON Schema поддерживает UTF-8 для корректного хранения кириллических текстов.


## 3) Стандарты данных и контракты

- Единицы измерения: SI (см, кг), timestamp — timestamptz (UTC).
- Идентификаторы: UUID для сущностей; telegramUserId хранится отдельно, линк через userId.
- RLS: доступ по userId; все запросы из n8n — через сервисный ключ со строгими политиками.
- JSON Schema:
    - airesponse.v1 — фиксированная структура: summary, red_flags[], lifestyle{}, self_care{}, talk_to_doctor{}, next_steps[1..2], confidence (0..1), disclaimer, sources?[].
    - Любые AI-ответы перед сохранением проходят JSON Schema валидацию в n8n.
- Enum’ы: источник, статус сессии и иные доменные enum — централизованно; изменения — миграциями.


## 4) Качество, безопасность и соответствие

- Валидация на каждом шлюзе: входящий Telegram intake → нормализация → schema validate → persist → ответ.
- Политика PII: PII изолирована, доступ только по строгой необходимости; маскирование в логах.
- Логи: структурированные, с уровнями, без PII; трассировка кореллируется через ids.
- Тестирование: контрактные тесты схем (JSON Schema), миграции, идемпотентность на повторных доставках Telegram событий.
- Нагрузочные и долговременные риски: проработка DLQ и повторов; оценка окон доставки в Telegram.


## 5) Правила интеграции с LLM

- LLM — инструмент форматирования и извлечения; источник истины — схемы и БД.
- Промпт-конструкция — из кода (n8n Function/Template) с жёсткой инструкцией выдавать строго JSON по схеме.
- Пост‑валидация обязательна. При несоответствии схеме — ретрай с сжатым контекстом; при исчерпании — DLQ.
- Никаких «домыслов» об идентификаторах и персональных данных: всё приходит из БД и intake.
**"Все промпты обязательно содержат инструкцию 'Отвечай исключительно на русском языке'"**

## 6) Telegram UX и поведение

- Команды: /start, /profile, /help, /new; CTA‑подсказки при ожидании.
- Ответы атомарны, с явными ссылками на исходное сообщение (messageId), без утечки PII.
- Повторная доставка/дубликаты: обрабатываются идемпотентно по messageId+telegramUserId.


## 7) n8n — обязательные паттерны

- Библиотека переиспользуемых узлов: Supabase Client, JSON Schema Validator, Logger, Retry Policy.
- Стандартизованные workflow: Intake → Resolve/Create User → Enrich Profile → Build Prompt → LLM Call → JSON Validate → Persist AI Response → Send Telegram → Error Handler.
- Секреты: только через n8n credentials (TELEGRAM_TOKEN, SUPABASE_URL/KEY, LLM_KEY).


## 8) Миграции и эволюция схем

- Все изменения в БД — через миграции, с сохранением совместимости вперёд, где возможно.
- Версионирование JSON Schema (airesponse.v1 → v2) и сопутствующие адаптеры при чтении.
- Чек‑лист обновления конституции обязателен при изменениях ключевых разделов.


## 9) Рабочий процесс SDD и ветвление

- Последовательность: /constitution → /specify → /plan → /tasks → implement → PR → merge.
- Каждая фича — своя ветка; линейные, маленькие задачи; автоматические проверки схем и миграций в CI.
- План и задачи обязаны соответствовать конституции; несоответствия — отклоняются и перерабатываются.


## 10) Неприменимые практики (запрещено)

- Сохранение AI‑ответов без валидации по JSON Schema.
- Обход RLS или смешение PII с доменными данными.
- Скрытые изменения схем/enum вне миграций и обзора.
- Хардкод секретов, логирование PII, произвольные ретраи без стратегии.


## 11) Метрики и наблюдаемость

- Ключевые метрики: доля валидных AI‑ответов, ретраи/дропауты, средняя латентность LLM/Telegram, частота DLQ, конверсия CTA.
- Алармы: рост DLQ, рост невалидных ответов, ошибки RLS/доступа, превышение латентности.


## 12) Процедура обновления конституции

- Инициируется через PR + constitution_update_checklist.md, c описанием мотивации и влияния.
- Обязателен аудит влияния на /plan и /tasks и, при необходимости, обновление шаблонов и промптов.
- Семантическое версионирование конституции; журнал изменений в начале файла.
