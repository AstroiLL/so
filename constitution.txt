# Конституция проекта Second Opinion (Spec Kit)

Главное: Конституция — это набор неизменяемых принципов и стандартов, которые направляют все спецификации (/specify), планы (/plan) и задачи (/tasks) в рамках SDD. Файл следует хранить в .specify/memory/constitution.md и поддерживать актуальным на протяжении всего жизненного цикла проекта.

## 1) Контекст проекта

- Название: Second Opinion
- Тип: Telegram-first медицинский ассистент с backend-first архитектурой
- Технологический контур: n8n для оркестрации, Supabase (PostgreSQL + RLS), Telegram Bot API, LLM через n8n HTTP Request/OpenAI node
- Основные артефакты: JSON Schema для AI-ответов и рекомендаций, ERD/DDL Supabase, нотация статусов с enum’ами, DLQ и идемпотентность в n8n
- Цель MVP: безопасный intake, нормализация данных, генерация структурированных рекомендаций (summary, red flags, lifestyle, self-care, talk-to-doctor, next steps, confidence, disclaimer) и диалог в Telegram[^4]

Этот раздел используется агентом как база при выработке решений в /plan и декомпозициях /tasks, обеспечивая «заземление» в реальных ограничениях и стандартах.[^1]

## 2) Архитектурные принципы (non-negotiable)

- Backend-first. Логика, валидация и контракты — на стороне бэкенда и схем данных. Telegram — транспорта и UX‑слой.[^4]
- Поток событий через n8n. Все бизнес-флоу — как явные workflow’ы. Обязательны: Retry с экспоненциальной паузой, DLQ, идемпотентность по messageId/композитным ключам.[^4]
- Договоры данных первичны. Любые AI-ответы должны соответствовать утверждённым JSON Schema. Любые изменения — через миграции и версионирование схем.[^4]
- Supabase как источник истины. Жёсткое соблюдение RLS, разделение PII и доменных данных, минимизация surface area REST/RPC.[^4]
- Детерминированные интеграции. Внешние вызовы (LLM, Telegram, Supabase) — обёрнуты в клиенты с явной сериализацией, логированием и контролем ошибок.[^4]
- Наблюдаемость и аудит. Полный audit log для критических операций; корреляция по userId/sessionId/messageId.[^4]
- Безопасность по умолчанию. Минимальные привилегии, секреты только в n8n credentials, строгие политики доступа к данным пользователя.[^4]
- Прозрачная эволюция. Любые изменения контракта/схемы/конституции — через PR, чек‑лист обновления, семантическое версионирование.[^1]


## 3) Стандарты данных и контракты

- Единицы измерения: SI (см, кг), timestamp — timestamptz (UTC).[^4]
- Идентификаторы: UUID для сущностей; telegramUserId хранится отдельно, линк через userId.[^4]
- RLS: доступ по userId; все запросы из n8n — через сервисный ключ со строгими политиками.[^4]
- JSON Schema:
    - airesponse.v1 — фиксированная структура: summary, red_flags[], lifestyle{}, self_care{}, talk_to_doctor{}, next_steps[1..2], confidence (0..1), disclaimer, sources?[].[^4]
    - Любые AI-ответы перед сохранением проходят JSON Schema валидацию в n8n.[^4]
- Enum’ы: источник, статус сессии и иные доменные enum — централизованно; изменения — миграциями.[^4]


## 4) Качество, безопасность и соответствие

- Валидация на каждом шлюзе: входящий Telegram intake → нормализация → schema validate → persist → ответ.[^4]
- Политика PII: PII изолирована, доступ только по строгой необходимости; маскирование в логах.[^4]
- Логи: структурированные, с уровнями, без PII; трассировка кореллируется через ids.[^4]
- Тестирование: контрактные тесты схем (JSON Schema), миграции, идемпотентность на повторных доставках Telegram событий.[^4]
- Нагрузочные и долговременные риски: проработка DLQ и повторов; оценка окон доставки в Telegram.[^4]


## 5) Правила интеграции с LLM

- LLM — инструмент форматирования и извлечения; источник истины — схемы и БД.[^4]
- Промпт-конструкция — из кода (n8n Function/Template) с жёсткой инструкцией выдавать строго JSON по схеме.[^4]
- Пост‑валидация обязательна. При несоответствии схеме — ретрай с сжатым контекстом; при исчерпании — DLQ.[^4]
- Никаких «домыслов» об идентификаторах и персональных данных: всё приходит из БД и intake.[^4]


## 6) Telegram UX и поведение

- Команды: /start, /profile, /help, /new; CTA‑подсказки при ожидании.[^4]
- Ответы атомарны, с явными ссылками на исходное сообщение (messageId), без утечки PII.[^4]
- Повторная доставка/дубликаты: обрабатываются идемпотентно по messageId+telegramUserId.[^4]


## 7) n8n — обязательные паттерны

- Библиотека переиспользуемых узлов: Supabase Client, JSON Schema Validator, Logger, Retry Policy.[^4]
- Стандартизованные workflow: Intake → Resolve/Create User → Enrich Profile → Build Prompt → LLM Call → JSON Validate → Persist AI Response → Send Telegram → Error Handler.[^4]
- Секреты: только через n8n credentials (TELEGRAM_TOKEN, SUPABASE_URL/KEY, LLM_KEY).[^4]


## 8) Миграции и эволюция схем

- Все изменения в БД — через миграции, с сохранением совместимости вперёд, где возможно.[^2][^3]
- Версионирование JSON Schema (airesponse.v1 → v2) и сопутствующие адаптеры при чтении.[^4]
- Чек‑лист обновления конституции обязателен при изменениях ключевых разделов.[^1]


## 9) Рабочий процесс SDD и ветвление

- Последовательность: /constitution → /specify → /plan → /tasks → implement → PR → merge.[^3]
- Каждая фича — своя ветка; линейные, маленькие задачи; автоматические проверки схем и миграций в CI.[^3]
- План и задачи обязаны соответствовать конституции; несоответствия — отклоняются и перерабатываются.[^3][^1]


## 10) Неприменимые практики (запрещено)

- Сохранение AI‑ответов без валидации по JSON Schema.[^4]
- Обход RLS или смешение PII с доменными данными.[^4]
- Скрытые изменения схем/enum вне миграций и обзора.[^4]
- Хардкод секретов, логирование PII, произвольные ретраи без стратегии.[^4]


## 11) Метрики и наблюдаемость

- Ключевые метрики: доля валидных AI‑ответов, ретраи/дропауты, средняя латентность LLM/Telegram, частота DLQ, конверсия CTA.[^4]
- Алармы: рост DLQ, рост невалидных ответов, ошибки RLS/доступа, превышение латентности.[^4]


## 12) Процедура обновления конституции

- Инициируется через PR + constitution_update_checklist.md, c описанием мотивации и влияния.[^1]
- Обязателен аудит влияния на /plan и /tasks и, при необходимости, обновление шаблонов и промптов.[^1]
- Семантическое версионирование конституции; журнал изменений в начале файла.

***

Как применить в репозитории:

- Разместить содержимое в .specify/memory/constitution.md.
- Поддерживать вместе с constitution_update_checklist.md.
- Перед запуском /plan и /tasks убедиться, что агент подтянул актуальный контекст конституции.[^3][^1]

Примечания:

- В Spec Kit конституция — официальный артефакт в папке memory, используемый всеми последующими шагами; её наличие и строгость — ключ к предсказуемому качеству результатов агентов.[^5][^2][^3][^1]
