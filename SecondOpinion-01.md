Базовый проект «Second Opinion» на n8n + Supabase (PostgreSQL)
Ключевой вывод: построить backend-first основу с тонким Telegram-клиентом. Все данные и бизнес-логика — в n8n и Supabase. Сразу заложить безопасные AI-промпты (без диагнозов/лекарств) и структурированное хранение данных. Основной поток: прием анкеты в Telegram → обогащение профилем из БД → генерация рекомендаций ИИ → парсинг и сохранение → ответ пользователю.
1. Цели и ограничения
    • Цель: собрать минимально-жизнеспособную backend-платформу Second Opinion для приема жалоб и анкет в Telegram и выдачи персональных рекомендаций по здоровью и образу жизни с помощью ИИ, учитывая данные из БД.
    • Архитектура: backend-first. Telegram-бот — тонкий клиент, вся логика и хранение — в n8n + Supabase.
    • Безопасность и комплаенс:
        ◦ Запрет ИИ ставить диагнозы/назначать лечение; обязательное дисклеймер-сообщение о необходимости консультации врача в каждом ответе.
        ◦ Ролевые промпты: системные инструкции ИИ обязательны.
        ◦ Контроль версий промптов и схем.
    • Масштабируемость: закладывать расширяемые таблицы и модульность n8n-воркфлоу.
2. Объем работ (MVP-основа)
2.1. Интеграции
    • Telegram Bot API: прием сообщений/форм, отправка сообщений, инлайн-кнопки.
    • Supabase:
        ◦ Таблицы PostgreSQL, политики RLS.
        ◦ REST/RPC доступ (Supabase API) из n8n.
    • Провайдер LLM (через n8n HTTP Request/OpenAI node): генерация рекомендаций.
2.2. Потоки n8n (высокоуровнево)
    1. Intake анкеты из Telegram
    • Триггер: Webhook от Telegram.
    • Шаги:
        ◦ Валидация сообщения, извлечение chat_id/user_id, текст жалобы/анкеты.
        ◦ Нормализация входа (JSON).
        ◦ Сохранение сырого сообщения в таблицу raw_intake.
        ◦ Поиск/создание пользователя в users по telegram_user_id.
        ◦ Парсинг анкеты (если структурированная форма) или сохранение как free-text.
        ◦ Лог: audit_log.
    2. Обогащение профилем и медданными
    • Шаги:
        ◦ Получить профиль, демографию, известные диагнозы/жалобы, базовые показатели, лекарства, аллергии, lifestyle (курение, сон, активность), прошлые рекомендации (для контекста).
        ◦ Построить агрегированный профильный контекст (JSON) для промпта.
    3. Генерация рекомендаций ИИ
    • Шаги:
        ◦ Сформировать системный промпт: безопасность, запреты, тон, формат ответа (JSON-схема).
        ◦ Пользовательский промпт: жалобы + профиль + анкета.
        ◦ Вызов LLM.
        ◦ Валидация/JSON Schema верификация ответа; при невалидности — повтор с указанием ошибок.
    4. Постобработка и сохранение
    • Шаги:
        ◦ Парсинг ответа по частям: краткая сводка, красные флаги, рекомендации по образу жизни (питание, сон, активность, стресс), self-care, что обсудить с врачом, источники/обоснование (если есть), уровень уверенности, хронология шагов.
        ◦ Сохранить в рекомендации + денормализованные таблицы.
        ◦ Привязать к сессии/запросу.
    5. Ответ пользователю в Telegram
    • Шаги:
        ◦ Сформировать человекочитаемый вывод (кратко, пунктами, безопасно, без диагнозов).
        ◦ Всегда добавить дисклеймер про консультацию врача.
        ◦ Отправить и зафиксировать message_id в БД.
    6. Мониторинг и ретраи
    • Шаги:
        ◦ Логи ошибок, DLQ, idempotency ключи.
        ◦ Метрики: время ответа, % невалидных JSON, % ретраев.
3. Датамодель (Supabase, PostgreSQL)
С учетом расширяемости и требований из TZ-light.[1]
    • users
        ◦ id (uuid, pk)
        ◦ telegram_user_id (text unique)
        ◦ created_at, updated_at
        ◦ pii: first_name, last_name, username (nullable)
        ◦ demographics: sex, birth_date
        ◦ contacts: phone, email (nullable)
        ◦ consent_flags: terms_accepted_at, data_processing_accepted_at
    • user_medical_profile
        ◦ id (uuid, pk), user_id (fk)
        ◦ height_cm, weight_kg, bmi (materialized/nullable)
        ◦ chronic_conditions (jsonb)
        ◦ medications (jsonb)
        ◦ allergies (jsonb)
        ◦ lifestyle (jsonb: smoking, alcohol, sleep_hours, activity_level, diet_notes)
        ◦ last_updated_at
    • questionnaires
        ◦ id (uuid, pk)
        ◦ code (text) — версия/тип анкеты
        ◦ schema (jsonb) — JSON Schema анкет
        ◦ is_active (bool)
    • user_questionnaire_submissions
        ◦ id (uuid, pk), user_id (fk), questionnaire_id (fk)
        ◦ raw_payload (jsonb)
        ◦ parsed_payload (jsonb)
        ◦ submitted_at
    • raw_intake
        ◦ id (uuid, pk), user_id (fk nullable), telegram_user_id (text), chat_id (text)
        ◦ message_id (text), message_ts (timestamptz)
        ◦ content_text (text), content_json (jsonb)
        ◦ source (enum: telegram)
        ◦ stored_at
    • sessions
        ◦ id (uuid, pk), user_id (fk)
        ◦ started_at, closed_at (nullable)
        ◦ context (jsonb) — краткий контекст обращения
        ◦ status (enum: open/closed)
    • ai_requests
        ◦ id (uuid, pk), session_id (fk), user_id (fk)
        ◦ model_name (text), prompt_system (text), prompt_user (text)
        ◦ request_payload (jsonb)
        ◦ created_at
    • ai_responses
        ◦ id (uuid, pk), ai_request_id (fk), user_id (fk), session_id (fk)
        ◦ raw_response (jsonb)
        ◦ structured_response (jsonb) — валидацией по JSON Schema
        ◦ safety_flags (jsonb) — блоки о рисках, триггеры
        ◦ created_at
    • recommendations
        ◦ id (uuid, pk), ai_response_id (fk), user_id (fk), session_id (fk)
        ◦ summary (text)
        ◦ red_flags (jsonb)
        ◦ lifestyle (jsonb: питание, сон, активность, стресс)
        ◦ self_care (jsonb)
        ◦ talk_to_doctor (jsonb)
        ◦ next_steps (jsonb) — пошаговый план на 1-2 недели
        ◦ confidence (numeric)
        ◦ disclaimer (text)
        ◦ created_at
    • audit_log
        ◦ id (uuid, pk), user_id (fk nullable), entity (text), entity_id (uuid), action (text)
        ◦ meta (jsonb), created_at
    • enums + вспомогательные:
        ◦ enum_source, enum_session_status
        ◦ json schema таблицы для ai_response, анкеты.
Индексы: telegram_user_id, user_id, session_id, created_at; полнотекстовый индекс по content_text (опционально).
RLS:
    • users: доступ владельцу.
    • Остальные таблицы: доступ по user_id, системным сервисным ключом из n8n.
4. AI-промптинг и безопасный формат ответа
Системный промпт (обязательно):
    • Запрет диагнозов, лекарств, дозировок.
    • Разрешены общие безопасные советы по образу жизни, self-care, красные флаги, «к врачу при …».
    • Обязателен дисклеймер «Не является медицинской консультацией. Обратитесь к врачу».
    • Тон: нейтральный, эмпатичный, краткий, структурированный.
Требуемый формат ответа ИИ (JSON):
    • summary: краткая сводка жалоб и контекста.
    • red_flags: список условий/симптомов, требующих очного обращения/неотложки.
    • lifestyle: питание, сон, активность, стресс (каждое — массив коротких рекомендаций).
    • self_care: домашние меры, безопасные.
    • talk_to_doctor: что обсудить с врачом/какие анализы возможно уместно обсудить (без назначения).
    • next_steps: пошаговый план на 1–2 недели.
    • confidence: 0–1.
    • sources_optional: массив кратких ориентиров (если применимо).
    • disclaimer: строка (стандартная).
JSON Schema должна применяться при валидации в n8n; при ошибке — рефразировать инструкцию и повторить 1–2 раза.
5. Telegram UX (тонкий клиент)
    • Начало: приветствие, согласие на обработку данных.
    • Команды: /start, /profile, /help, /new.
    • Формы:
        ◦ Анкета с жалобой: свободный текст + инлайн шаги (длительность, интенсивность, сопутствующие, прошлые действия, цели).
        ◦ Инлайн-кнопки: «Отправить», «Изменить», «Добавить деталь».
    • Ответ: структурированный вывод по разделам (кратко), CTA: «Показать подробный план», «Обсудить с врачом».
    • Всегда включать дисклеймер.
6. n8n — архитектура воркфлоу
    • Workflows:
        a. Telegram Intake Webhook
        b. User Resolve/Create + Persist Raw
        c. Profile Enrichment (Supabase Select)
        d. Build Prompt (Function/Code node)
        e. LLM Call + JSON Validate
        f. Persist AI Response + Recommendations
        g. Send Telegram Message
        h. Error Handler (перехватчик) + DLQ
    • Reusable Nodes:
        a. Supabase Client (HTTP request с ключом)
        b. JSON Schema Validator
        c. Logger
        d. Retry policy (exponential backoff)
    • Secrets в n8n credentials: TELEGRAM_TOKEN, SUPABASE_URL/KEY, LLM_KEY.
7. Нефункциональные требования
    • Производительность: ответ ≤ 10–20 сек в типовом случае (кеш профиля, компактные промпты).
    • Наблюдаемость: структурированные логи, корреляционные ids.
    • Надежность: ретраи 3 попытки; идемпотентность на message_id.
    • Версионирование: версии анкет, версионирование промптов и схем.
    • Безопасность: RLS, минимальные привилегии, шифрование секретов в n8n, удаление PII из логов.
8. Пошаговый план внедрения
    1. БД (Supabase)
    • Создать таблицы и enum’ы, настроить индексы.
    • Включить RLS, политики доступа.
    • Загрузить JSON Schema: анкета_v1, ai_response_v1.
    • Тестовые данные пользователя и анкеты.
    2. Telegram бот
    • Зарегистрировать BotFather, получить токен.
    • Настроить webhook на n8n.
    • Базовые команды и форматирование ответа.
    3. n8n Workflows
    • Intake → Persist → Enrich → Prompt → LLM → Validate → Persist → Reply.
    • Ошибкообработка и DLQ.
    4. AI-интеграция
    • Системный промпт + формат JSON.
    • Валидация, ретраи, контроль длины.
    5. Тестирование
    • Юзкейсы: полная анкета, короткая жалоба, отсутствие профиля, повторные сообщения, невалидный ответ LLM.
    • Нагрузочные: 50–100 запросов/ч.
    • Безопасность: попытки получить диагноз/лекарства.
    6. Документация
    • ER-диаграмма, схемы JSON, примеры запросов/ответов, политики RLS.
    • Чек-лист релиза.
9. Критерии приемки (MVP)
    • Принимает анкеты в Telegram, распознает пользователя по telegram_user_id и сохраняет сырье.
    • Подтягивает медданные пользователя из БД и формирует промпт.
    • Генерирует структурированный JSON-ответ ИИ, проходит валидацию.
    • Сохраняет рекомендации в БД и отправляет краткий ответ пользователю с дисклеймером.
    • Логи и ретраи работают; RLS включен.
    • Документация базы и воркфлоу предоставлена.
    • Тестировать функционал возможно сразу по мере создания.
10. Оценка трудозатрат (грубая, MVP)
    • Схема БД, RLS, миграции: 12–16 ч
    • Интеграция Telegram (webhook, команды, разметка): 8–12 ч
    • n8n воркфлоу (интейк, обогащение, LLM, валидация, сохранение, ответ): 20–28 ч
    • Промптинг и JSON Schema, ретраи: 8–12 ч
    • Логи, наблюдаемость, идемпотентность: 6–10 ч
    • Тестирование (функц./нагруз./безопасность): 10–16 ч
    • Документация: 6–8 ч
Итого: 70–102 ч на MVP-основу. 2-3 рабочие недели.
11. Риски и допущения
    • Риск: невалидные ответы LLM → смягчается JSON Schema и ретраями.
    • Риск: задержки Telegram/LLM → таймауты и очереди.
    • Допущение: провайдер LLM стабилен и доступен в проде.
    • Допущение: согласие пользователя на обработку персональных данных получено.
Учитывает требования TZ-light: backend-first, хранение сырых анкет и структурированных ответов, формирование сложного промпта, парсинг и безопасные ответы с дисклеймером.
